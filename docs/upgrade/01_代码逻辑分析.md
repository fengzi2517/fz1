# S1 · role_play 代码逻辑分析

> 分析对象：`fengzi5422/role_play` @ `2be800d`。所有结论均以代码为准（文件:行号可跳转核对），设计文档仅作背景参考。
> 重点：记忆链路、多对话管理、群聊管理三大逻辑链条的端到端梳理 + 问题清单。

## 1. 总体架构

```
Flutter 前端 (frontend/lib)                 Python FastAPI 后端 (backend/app)
┌─────────────────────────┐   HTTP/SSE/WS   ┌──────────────────────────────┐
│ ChatProvider   单聊状态  │ ──────────────► │ api/chat      单聊 SSE        │
│ GroupProvider  群聊状态  │ ◄────────────── │ api/groups    群聊 SSE + WS   │
│ ConversationProvider 列表│                 │ api/conversations 会话列表    │
│ VoiceProvider  语音      │                 │ api/characters/memory/asr/tts │
└─────────────────────────┘                 │ services: chat / memory /     │
                                            │ distill / group / idle /      │
Android 壳 (app/, 仅 WebView 容器)           │ character / asr / tts         │
tools/whisper: 本地 ASR (Windows exe)        │ llm/adapter: OpenAI 兼容协议   │
                                            └──────────────┬───────────────┘
                                                           │ 纯文件存储（无数据库）
                                                           ▼
                                            data/users/{uid}/…（见 §2）
```

- 后端约 2900 行 Python，前端约 25 个 Dart 文件；无测试、无鉴权（`user_id` 由请求方自报，前端硬编码 `user_001`，`frontend/lib/config/api_config.dart:26`；CORS 全开，`backend/app/main.py:12-18`）。
- LLM 走 OpenAI 兼容 `/chat/completions`，默认 DeepSeek，支持请求级 model/temperature 覆盖与备用模型回退（`backend/app/llm/adapter.py`）。
- 语音：ASR 支持本地 whisper.cpp（默认指向 Windows exe，Linux 部署不可用）或 OpenAI 兼容云端；TTS 走 SiliconFlow MOSS-TTSD（`backend/app/config.py:39-61`）。

## 2. 数据布局（文件即数据库）

路径函数见 `backend/app/config.py:64-87`：

```
data/users/{user_id}/
├── profile.md                     # 用户档案（front matter + md 正文）
├── long-term.md                   # 用户级长期记忆，跨角色共享，按日期分节
├── characters/{character_id}/
│   ├── profile.md                 # 角色人设（LLM 解析后的结构化 md）
│   ├── memory.md                  # 角色×用户 记忆（含"群聊见闻"），按日期分节
│   └── sessions/{session_id}/
│       ├── history.jsonl          # 单聊消息流（role/content/timestamp）
│       └── summary.md             # 分段摘要；front matter 存 distilled_upto 游标
└── groups/{group_id}/
    ├── meta.json                  # 群名、成员 ids、distilled_upto 游标
    ├── history.jsonl              # 群消息流（额外带 character_id/name）
    └── summary.md                 # 群聊概要；front matter 存 summary_upto 游标
```

记忆 md 格式：`## YYYY-MM-DD` 日期分节（倒序）+ `- HH:MM  内容` 条目，由 `markdown_parser.py` 解析、`memory_service._rebuild_memory_body()` 重建（`backend/app/services/memory_service.py:304-328`）。

## 3. 记忆链路（核心链条 ①）

### 3.1 写入侧：消息落盘 → 蒸馏 → 长期记忆

```
用户发消息 ─► append_message(history.jsonl)          chat_service.py:81-87
LLM 回复完 ─► append_message(history.jsonl)          chat_service.py:120-127
                    │
        ┌───────────┴──────────── 蒸馏触发（4 个入口）────────────┐
        │ ① POST /api/chat/end（前端离开聊天页）      api/chat.py:112-119
        │ ② 会话软轮换：GET /history 发现 ≥60 条或跨天 → 后台蒸馏并令前端开新会话
        │                                    api/chat.py:38-43,60-66
        │ ③ IdleSweeper：每 300s 扫描全部用户，history.jsonl mtime 闲置 ≥1800s
        │   的会话兜底蒸馏（杀 App 场景）              idle_service.py:48-95
        │ ④ 群聊：每轮用户发言后 maybe_refresh，未覆盖消息 >30 条即后台蒸馏
        │                                    group_service.py:380-398
        └────────────────────────────────────────────────────────┘
                    ▼
distill_session（增量，游标=summary.md 的 distilled_upto）  distill_service.py:21-90
  1. 读全量 history（limit 2000），跳过已蒸馏部分；新增 <2 条则攒着
  2. SUMMARY_PROMPT → LLM 生成分段摘要 → 追加 summary.md「片段 N（第 x-y 条）」
  3. EXTRACT_MEMORY_PROMPT → LLM 从摘要提取 JSON：
     { user_preferences: [...], character_relationship: [...] }
  4. 逐条去重（jieba 分词，与最近 20 条关键词重合率 >0.6 判重）
     user_preferences      → users/{uid}/long-term.md
     character_relationship → characters/{cid}/memory.md
```

关键细节：
- **增量游标**防重复蒸馏：`distilled_upto` 存 summary.md front matter（`distill_service.py:36-66`）；群聊双游标：`meta.json.distilled_upto`（记忆提取）与 `summary.md.summary_upto`（概要）各自独立推进（`group_service.py:406-416,577-597`）。
- **去重**是纯词面重合：`is_duplicate()` 用 jieba 词集交集占比 > `RECALL_KEYWORD_OVERLAP_THRESHOLD=0.6`（`memory_service.py:282-300`，`config.py:29`）。同义改写判不出重复，矛盾事实（"用户喜欢猫"→后来"用户养了狗并讨厌猫"）不会更新旧条目，只会并存。
- **每次追加 = 全文件重写**：`append_long_term` 读出全部条目→追加→按日期重排→整体写回（`memory_service.py:41-78`）。无文件锁，并发蒸馏（如 /end 与 IdleSweeper 同时触发）存在读-改-写竞态丢数据风险。
- 蒸馏失败仅 print 日志，游标不推进则下次重试（`distill_service.py:88-90`）；但**摘要已写入而提取失败**时游标已推进，该段记忆永久丢失（`distill_service.py:58-68` 先写 summary 再提取，提取异常被外层 catch 吞掉）。

### 3.2 读取侧：Prompt 组装与 recall

单聊 `build_messages`（`chat_service.py:23-60`）固定顺序：

```
[system] SYSTEM_PROMPT（角色扮演行为准则 + 记忆使用说明）
[system] 【角色设定】characters/{cid}/profile.md 正文
[system] 【用户档案】users/{uid}/profile.md 正文
[user/assistant] 最近 20 条 history（MAX_HISTORY_MESSAGES=20，按条数不按 token）
[system] 【回忆起的相关信息】← 仅当 recall 命中（见下）
[user]   当前输入
```

recall 触发与检索（`chat_service.py:89-99`，`memory_service.py:209-278`）：
1. **规则预判**：用户消息含 `RECALL_TRIGGER_KEYWORDS`（"记得/上次/约定/我喜欢…" 共 16 个，`prompts.py:110-115`）才检索。`RECALL_TOOL` 工具定义存在但**从未使用**（`prompts.py:20-36`；`chat_service.py:106` 注释明确不传 tools）——即 LLM 无法主动决定回忆。
2. jieba 切 query（保留长度 >1 的词）→ 在 long-term.md 与 memory.md 中**子串匹配**计分：`score = 命中词数 × 1/(1+天数差)`，取 top 10（`RECALL_TOP_K`）。
3. 零命中兜底：注入最近 8 条记忆（`get_recent_memories`），避免"你还记得我叫什么"这类泛问题答"不记得"。

**重大缺口（代码证实）**：
- `summary.md` 的分段摘要**从不回注单聊上下文**——`chat_service.py` 无任何读取 summary 的代码。蒸馏出的摘要只用于提取记忆条目，会话轮换后新会话对旧剧情近乎失忆，除非用户话里恰好带触发词。
- `write_user_profile()` 全仓库**无调用方**——用户档案永远是默认模板（`memory_service.py:330-339`），"用户画像随对话成长"没有闭环。
- 无向量检索、无语义匹配、无 token 预算控制、无遗忘/衰减机制（仅 recall 计分带时间衰减权重）。

### 3.3 群聊记忆（读写两侧都更强）

每个成员发言前的上下文（`group_service.py:268-303`）：

```
[system] GROUP_SYSTEM_PROMPT（成员名单+群聊规则：1~3句/80字内、不替他人发言）
[system] 【你的角色设定】该成员 profile.md
[system] GROUP_CONTEXT_TEMPLATE：
    【群聊概要】summary.md 正文（尾部截断 4000 字符）      ← 单聊没有的待遇
    【更早的群聊片段】30 条窗口之外的历史按 jieba 关键词召回 top6
    【你记得的关于用户的事】该成员 recall(top6)（long-term + 自己的 memory.md）
    【最近的群聊】最近 30 条渲染成 "名字: 内容" 纯文本
    【当前发言者】{speaker}
[user] 当前用户消息
```

群聊蒸馏 `distill_group`（`group_service.py:418-475`）：
- 先增量更新群概要（所有角色共享）；
- 再**按每个成员视角**各调一次 LLM（`GROUP_MEMORY_EXTRACT_PROMPT`），提取 `{user_preferences, character_relationship, group_events}`；
- `group_events` 加"（群聊见闻）"前缀写入该成员自己的 memory.md → 实现"角色各自记住群里发生的事"，跨群/单聊可见。
- 成本：N 成员 = N+1 次 LLM 调用/轮蒸馏；4 成员群蒸馏一次 5 连调，串行执行。

       ├─ 取该角色 mtime 最新的会话                 memory_service.py:191-205
       ├─ 若 ≥60 条 或 首条消息日期≠今天（软轮换）：

### 4.2 会话列表（消息页）

`GET /api/conversations`（`api/conversations.py`）：遍历所有角色取各自最新会话的最后 1 条 + 所有群的最后 1 条，拼 preview（40 字），按时间倒序合并返回。**没有会话级列表**——一个角色只露出"最近一个会话"，旧会话在 UI 上不可达（数据还在磁盘）。

## 5. 群聊管理（核心链条 ③）

### 5.1 编排流程（`GroupChatService.chat_stream`，group_service.py:207-350）

```
用户消息（SSE /api/groups/{id}/chat 或 WS /ws）
  1. 校验群/目标成员（target 模式先校验再落盘）
  2. 取最近 30 条历史 → 写入用户消息 → maybe_refresh 后台蒸馏
  3. 准备共享上下文：群概要 + 关键词召回旧片段 + 各成员私有记忆
  4. 发言调度：
     ├─ target 模式：仅指定角色 1 人发言（前端点选"只让 TA 回"）
     └─ round_robin：全员发言，起点 = 用户发言轮次 % 成员数 轮转
        （user_turns 只统计最近 30 条窗口内的用户消息！）
  5. 逐成员串行流式生成（max_tokens=300），事件流：
     start → token* → done →（下一成员）… → end
  6. 每个成员发言完立即 append 到群 history.jsonl
```

### 5.2 WebSocket 插话打断（M2.1，api/groups.py:104-173）

- 每连接维护 `{task, interrupt: asyncio.Event}`；用户新消息到达时 `interrupt.set()` → `await 旧task`（旧轮在 token 循环里检查 event，尽快收尾）→ 换新 Event 开新轮。
- **被打断的半截回复会保存**（`full.strip()` 非空即落盘，group_service.py:330-334），剩余成员不再发言，发 `interrupted` 事件。
- 前端 GroupProvider：WS 优先、3s 连接超时回退 SSE；`_pendingRounds` 计数处理插话时新旧两轮并存的 end 事件（group_provider.dart:34-35,212-216）；WS 断线自动复位流式状态防输入框卡死。

## 6. 横切问题（影响所有链条）

1. **存储引擎**：全文件读-改-写，无锁、无索引、无事务。history 每次请求全量读入再切片（`get_recent_history`/`count_history`），消息量增长后 O(n) 劣化；long-term.md 无限增长且每次追加全量重写。
2. **检索质量**：jieba 子串匹配无语义能力（"我们上次去的那家餐厅"召回不到"和用户去了海底捞"）；无 embedding、无 BM25、无混合检索。
3. **记忆治理缺失**：无更新/合并/冲突消解/重要性分级/遗忘曲线；去重仅词面 0.6 阈值。
4. **LLM 适配层**：fallback 条件 `model != LLM_FALLBACK_MODEL and LLM_FALLBACK_MODEL != model` 两条件等价（恒等于一个条件），且 `model=None` 时与 fallback 比较逻辑失真；流式中途失败切 fallback 会**重复输出已 yield 的 token**（adapter.py:64-73）；无 429 退避重试、无 JSON mode/结构化输出保证（全靠正则 `\{.*\}` 贪婪抠 JSON）。
5. **可观测性**：全部 print 日志，无结构化日志/指标/追踪；蒸馏失败静默。
6. **安全**：无鉴权、CORS `*`、user_id 路径拼接未校验（`../` 可穿越目录读任意文件——`get_user_dir` 直接拼路径，config.py:64-66）、删除接口无确认。
7. **工程化**：零测试；`@app.on_event` 已废弃 API；datetime.now() 无时区；Windows 专用 ASR 二进制入库（仓库体积大）。
8. **角色卡**：创建时 LLM 解析后**原始人设文本即丢弃**（只存解析后的结构化 md，character_service.py:140-162），编辑再解析是有损往返；不兼容社区角色卡标准（V2/V3 PNG 卡），无头像/表情差分/开场白/示例对话字段。

## 7. 亮点（升级时应保留的设计）

- 记忆全部人类可读 Markdown + JSONL，可手工审计/编辑/迁移，隐私友好（数据全本地）。
- 增量蒸馏游标设计（distilled_upto / summary_upto）正确解决了重复蒸馏问题。
- 四路蒸馏触发（主动 end / 软轮换 / 闲置巡检 / 群聊阈值）覆盖完整，杀 App 不丢记忆。
- 群聊"按成员视角分别提取记忆 + 群聊见闻"是同类开源里少见的正确设计。
- WS 插话打断 + SSE 回退 + pendingRounds 的客户端状态机处理得相当细。
- recall 零命中兜底最近记忆，避免"我不记得"体验灾难。

## 8. 语音链路（M1，补充梳理）

```
Android 端（MethodChannel 'ai_roleplay/asr'，voice_service.dart）
  优先：系统 SpeechRecognizer 实时识别（onResult/onLevel 回调）
  兜底：原生录音 16k 单声道 WAV → POST /api/asr/transcribe（≤10MB，仅 WAV）
        后端 asr_service：local whisper.cpp 子进程（180s 超时）
                          或 OpenAI 兼容 /audio/transcriptions
  TTS：优先云端 GET /api/tts/speech?text&speed → mp3
        （SiliconFlow MOSS-TTSD，300 字符截断，sha1 磁盘缓存 cache/tts/）
        原生播放器 playUrl 播放，onTtsDone 回调；失败回退 flutter_tts 系统合成
  朗读前清洗：去括号动作描写、去 markdown 符号（voice_service.dart:328-333）
```

- 能力探测：`/api/asr/status`、`/api/tts/status`，App 启动时决定是否启用录音上传/云端朗读；所有语音异常被吞掉，不阻塞文字对话（设计正确）。
- 问题：①半双工"按住说话→整段回复→整段朗读"，无流式 TTS/语音打断/VAD；②TTS 走 GET query 传文本（长文本超 URL 限制、文本进访问日志）；③本地 whisper 默认 Windows exe，Linux 服务端不可用；④单一全局音色，无角色专属音色；⑤云端 TTS 仅 Android 路径启用（`_speakCloud` 走原生通道），Web/iOS 无云端朗读。

## 9. 三大链条一句话总结

- **记忆链路**：文件式三层记忆（会话 history → 会话 summary → 用户/角色长期 md），LLM 两段式蒸馏（摘要→提取），jieba 词面检索 + 规则触发；*摘要不回注、画像不更新、无语义检索*是三大断点。
- **多对话管理**：角色→多会话目录 + mtime 取最新 + 60 条/跨天软轮换；*旧会话不可达、无消息操作、无 token 预算*。
- **群聊管理**：≤4 成员，全员轮转或指定发言，共享概要+私有记忆双通道，WS 可插话打断；*无智能调度、无关系状态、串行延迟*。

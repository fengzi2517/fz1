## 二、后端设计

### 2.1 数据目录

```
data/users/{user_id}/groups/{group_id}/
├── meta.json        # {group_id, name, character_ids, created_at}
└── history.jsonl    # {role, content, character_id, name, timestamp}
```

与单聊不同，群聊的每条消息都记录 `character_id` 与 `name`，用于区分发言人。

### 2.2 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/groups` | 创建群聊（1~4 个角色） |
| GET | `/api/groups?user_id=` | 群聊列表（含成员） |
| GET | `/api/groups/{id}?user_id=` | 群聊详情 |
| DELETE | `/api/groups/{id}?user_id=` | 删除群聊 |
| GET | `/api/groups/{id}/history?user_id=` | 群聊历史 |
| POST | `/api/groups/{id}/chat` | 群聊发言（SSE，支持 reply_mode/target） |
| POST | `/api/groups/{id}/end?user_id=` | 触发群聊记忆蒸馏 |
| WS | `/api/groups/{id}/ws?user_id=` | 群聊实时通道（支持中途插话） |

### 2.3 群聊编排

1. 先读取历史（不含本条用户消息），再把用户消息写入 `history.jsonl`
2. 按「用户已发言轮次 % 成员数」决定先手，实现顺序轮换
3. 每个角色依次发言，单角色 System Prompt 包含：
   - 群成员清单（名字 + 一句话简介）
   - 该角色自己的完整人设
   - 最近 20 条群聊上下文（带发言人）
   - 「当前发言者」指令：只输出这一角色的话
4. 单角色回复上限 300 tokens，并提示「1~3 句、80 字以内」，避免 N 个角色拖长等待
5. 每个角色的完整回复写入历史，带 `character_id` 与 `name`

### 2.4 SSE 事件协议

```json
{"type":"start","character_id":"c_x","name":"沈砚"}
{"type":"token","content":"山居","character_id":"c_x","name":"沈砚"}
{"type":"done","character_id":"c_x","name":"沈砚"}
{"type":"end"}
```

前端按 `start` 新建气泡、按 `token` 追加、按 `done` 收尾，天然支持多角色交错渲染。

### 2.5 群聊记忆蒸馏（M2.1）

群聊结束后，按「每个角色各自的视角」把群聊记录提炼为长期记忆，而不是共享一份摘要：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/groups/{id}/end?user_id=` | 触发后台蒸馏（BackgroundTasks，不阻塞返回） |

实现要点：

1. 每个群聊在 `meta.json` 中维护 `distilled_upto` 游标，只处理新增消息，重复调用不会重复写入
2. 对每个成员角色，用 `GROUP_MEMORY_EXTRACT_PROMPT` 以该角色视角提取：
   - `user_preferences` → 写入用户档案
   - `character_relationship` → 写入该角色的 `memory.md`
3. 群聊记录按「角色名: 内容」拼成 transcript，只提取与用户相关的信息
4. 前端在群聊页 `PopScope` 离开时调用 `endGroup()`，异步触发、失败不影响返回
5. 后端 `IdleSweeper` 每 5 分钟巡检一次，`history.jsonl` 闲置超过 30 分钟的群聊会自动蒸馏，
   覆盖用户直接杀进程、不触发 `endGroup()` 的情况（验证 10/10）

### 2.6 角色库编辑 / 删除（M2.1）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/characters/{id}?user_id=` | 详情（含 `raw_content`，编辑回填用） |
| PUT | `/api/characters/{id}` | 就地覆盖人设（保留 `character_id`） |
| DELETE | `/api/characters/{id}?user_id=` | 删除角色目录 |

修复要点：原 `update_character` 内部调用 `create_character`，会先生成一个新的角色目录再写回旧目录，导致「编辑一次多一个角色」。现拆出 `_parse_profile()`（只解析不落盘），创建与更新共用，更新时只重写原目录的 `profile.md`。

前端交互：角色卡右侧 `PopupMenuButton` →「编辑人设」弹窗（名称 + 人设正文，Markdown 可改）/「删除角色」二次确认。

### 2.7 发言控制（M2.1）

`POST /api/groups/{id}/chat` 与 WebSocket 消息都支持：

| 字段 | 取值 | 说明 |
|------|------|------|
| `reply_mode` | `round_robin` / `target` | 自由轮询 / 只让指定角色回应 |
| `target_character_id` | `c_xxx` | `target` 模式下必填 |

- `target` 模式在校验目标角色属于该群之后才写入用户消息，非法目标返回错误且不污染历史
- 前端群聊页右上角「选择谁回应」底部弹层：自由轮询 + 各成员；选中后输入框上方显示「仅 X 回应」，可一键恢复

### 2.8 WebSocket 与中途插话（M2.1）

| 项 | 说明 |
|----|------|
| 端点 | `WS /api/groups/{group_id}/ws?user_id=` |
| 上行 | `{"type":"message","content":"...","reply_mode":"...","target_character_id":"..."}`、`{"type":"ping"}` |
| 下行 | `start / token / done / interrupted / end / error / pong`（与 SSE 一致，另有 `interrupted`） |

插话流程：

1. 当前轮发言中收到新消息 → 设置 `interrupt_event`
2. 正在生成的 token 循环检测到事件后立即停止，已输出的部分照常落库
3. 推送 `interrupted`（附角色），结束本轮剩余角色的发言
4. 主循环 `await` 旧轮收尾后，用新的 `reply_mode` 开启下一轮

前端使用 `dart:io` 的 `WebSocket`（不引入额外依赖）；连接失败自动回退 SSE，
回退后恢复「发言中禁止输入」的旧行为。后端 `requirements.txt` 新增 `websockets` 依赖。

### 4.6 群聊记忆 v2（2026-11-15）

目标：每个角色有自己的记忆，同时也能「看到」群聊的全部内容，像真人一样。

| 机制 | 实现 |
|------|------|
| 最近上下文 | `GROUP_HISTORY_WINDOW` 从 20 提升到 30 条 |
| 更早的群聊 | `GroupService.search_history()` 用 jieba 关键词在窗口外的历史中召回相关片段 |
| 群聊概要 | 蒸馏时增量生成 `groups/{id}/summary.md`（`summary_upto` 游标），每轮发言注入 |
| 个人记忆 | 每轮发言前按用户消息 `recall` 该角色自己的 `memory.md` + 用户长期记忆 |
| 群聊见闻 | 蒸馏 Prompt 新增 `group_events`，把群里发生的事写进每个角色独立的记忆 |

每轮 System Prompt 由「群聊概要 + 更早片段 + 你的记忆 + 最近 30 条」组成，
因此角色能记得很久以前群里说过的话，也能从自己的视角记住其他角色和用户的事。

### 4.8 群聊概要懒加载（2026-11-15）

问题：概要原本只在 `/end` 或闲置巡检（30 分钟无消息）时生成。用户长时间泡在群里、不退出会话时，
超出最近 30 条的内容不会进入任何角色的上下文，「看到群聊的所有消息」在长会话中会退化。

实现：

| 环节 | 实现 |
|------|------|
| 计数 | `GroupService.count_history()` 读取历史总条数 |
| 判定 | `GroupDistillService.maybe_refresh()`：`总数 - summary_upto > GROUP_HISTORY_WINDOW(30)` 才触发 |
| 执行 | `asyncio.create_task(distill_group)` 后台补概要 + 角色记忆，不阻塞本轮发言 |
| 去重 | `_refreshing` 集合保证同一群聊同时只跑一次；已有覆盖时不重复蒸馏 |

每轮发言开始前调用一次判定（仅两次文件读取），因此长会话里角色始终能拿到概要 + 最近 30 条 + 关键词召回。

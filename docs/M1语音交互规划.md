# AI 角色扮演聊天工具 - M1 语音交互开发构思与规划

> 版本：v1.0 | 日期：2026-11-13 | 状态：待确认
> 上游文档：概要设计.md、详细设计.md、开发规划.md

## 一、M1 定位与范围

### 1.1 阶段目标

M0 已经跑通「文字对话 + 记忆闭环」，M1 的目标是让交互从**打字**升级为**说话**：

1. 用户长按说话 → 自动转文字 → 发送（ASR）
2. AI 回复可播放语音，支持自动朗读（TTS）
3. 每个角色拥有独立音色，强化角色扮演的沉浸感
4. 记忆检索从「关键词命中」升级为「关键词 + 语义」双路

### 1.2 明确不做的部分

| 不做 | 原因 |
|------|------|
| 实时双工语音通话（像 GPT-4o 那种打断式对话） | 需要 WebSocket 流式 ASR + 流式 TTS + VAD，复杂度远超 M1，放到 M3 |
| 声纹识别 / 情绪识别 | 与「角色扮演陪伴」核心价值弱相关 |
| 多角色群聊 | M2 范围 |

### 1.3 M0 遗留问题的处理

M1 开始前需要顺手修掉两处 M0 遗留（不单独占里程碑）：

| 问题 | 现状 | M1 处理方式 |
|------|------|------------|
| 会话无限增长 | 同一角色永远复用同一个 `session_id`，`history.jsonl` 持续变大 | 加「软轮换」：单会话超过 N 条（建议 60）或跨天时，自动开新会话，旧会话立即蒸馏 |
| 重复蒸馏 | 每次离开聊天页都触发蒸馏，会话越长重复成本越高 | 在 `summary.md` front matter 记录 `distilled_offset`（已处理到第几条消息），增量蒸馏 |
| recall 关键词漏召回 | 已加「零命中时注入最近 8 条」兜底，仍非语义检索 | 见第五章，M1 内升级为混合检索 |

> 说明：会话连续性问题（离开再进消息丢失）已在 2026-11-13 修复，不属 M1 范围。

## 二、语音链路总体设计

### 2.1 链路 A：语音输入（ASR）

```
用户长按麦克风
      │
      ▼
 Flutter 录音（record 插件，amr/wav，16kHz 单声道）
      │  松手结束
      ▼
 POST /api/voice/asr  (multipart: audio)
      │
      ▼
 VoiceService → ASR Provider（设备端直转 / 云端 API）
      │
      ▼
 返回 {text}
      │
      ▼
 文本回填输入框（用户可编辑）→ 走现有 POST /api/chat/send
```

**关键设计：ASR 只负责「音频 → 文字」，不直接触发对话。** 文本回填后由用户确认发送，避免识别错误直接污染对话和记忆。

### 2.2 链路 B：语音输出（TTS）

```
SSE 流式回复累积中
      │ 遇到句末标点（。！？；\n）且长度 ≥ 12 字
      ▼
 切句 → POST /api/voice/tts {text: 单句, voice_id}
      │
      ▼
 返回音频（mp3/wav）→ just_audio 入播放队列
      │  边合成边播放，不等全文
      ▼
 用户切走 / 发新消息 → 立即停止播放
```

**关键设计：按句切分做「流式 TTS」**，让首音延迟从「整段合成」的 2~3s 降到 1s 内。整段合成只作为兜底。

### 2.3 语音状态机（前端）

```
idle ──按下──► recording ──松手──► transcribing ──► textReady ──发送──► chatting
  ▲                │上滑取消                │失败                              │
  └────────────────┴────────────────────────┴──────────────────────────────────┘
                                     ▲
                          speaking（TTS 播放中）──► 被打断 ──► idle
```

规则：
- `recording` / `transcribing` 期间输入框禁用，防止并发提交
- `speaking` 时用户发送新消息 → 立即 `stop()`，不排队
- 录音时长上限 60s，超时自动停止并转写

## 三、ASR / TTS 选型（需决策）

### 3.1 约束前提

当前 LLM 用的是 DeepSeek（`.env` 中 `LLM_BASE_URL=https://api.deepseek.com/v1`）。**DeepSeek 不提供 ASR / TTS 接口**，因此语音能力必须引入新的供应商，或改用设备端能力。

### 3.2 方案对比

| 维度 | A. 设备端（系统能力） | B. 云端 API（阿里云/火山/讯飞） | C. 自建（Whisper + 本地 TTS） |
|------|----------------------|-------------------------------|------------------------------|
| 接入成本 | 极低，两个 Flutter 插件 | 中，需注册+实名+签名鉴权 | 高，需部署模型服务 |
| 费用 | 免费 | 按量计费（ASR 约 2~3 元/小时，TTS 约 3~5 元/万字符） | 电费/GPU 成本 |
| 中文识别质量 | 依赖机型，主流安卓机尚可 | 好且稳定 | Whisper large 很好 |
| 音色质量 | 系统音色，机械感明显 | 好，可做情感/角色音色 | 取决于模型，可克隆音色 |
| 角色音色定制 | **做不到** | 支持多音色，可绑定角色 | 支持音色克隆 |
| 首音延迟 | < 300ms | 300~800ms | 视部署而定，通常 > 1s |
| 隐私 | 音频不出设备 | 音频上传第三方 | 全本地 |
| Web 端可用性 | 差（浏览器 API 各异） | 好 | 好 |
| Android 离线可用 | 是 | 否 | 是 |

### 3.3 推荐路线：分两步走

**M1.0（先跑通链路）→ 设备端方案 A**
- ASR：`speech_to_text` 插件（Android 系统语音识别）
- TTS：`flutter_tts` 插件（Android 系统 TTS，`zh-CN`）
- 价值：零成本、当天可验证交互是否好用；把状态机、录音 UI、播放队列这些**真正的产品复杂度**先解决掉
- 风险：音色差、部分国产 ROM 语音服务不完整

**M1.1（决定产品质感）→ 云端方案 B**
- 后端 `VoiceService` 抽象出 `ASRProvider` / `TTSProvider` 两个接口，M1.0 的插件只在前端，M1.1 切换时**只改前端调用方向，不改状态机**
- 供应商优先考虑火山引擎（音色最丰富）或阿里云（文档完善）
- 角色音色：`characters/{id}/profile.md` 增加 `voice_id` 字段，设置面板可选

> 关键：**先抽象后实现**。M1.0 也不要让插件调用散落在 UI 里，统一收敛到 `VoiceService`（前端），后续换成 HTTP 调用只需替换实现类。

### 3.4 需要你确认的决策

1. 是否接受「M1.0 先用系统音色跑通，M1.1 再接云端」的两步走？
2. 若直接上云端，倾向哪家（火山/阿里/讯飞），以及是否已有账号和额度？
3. 主要验证设备是 Android 真机、模拟器，还是先用 Web 看效果？（Web 对设备端方案支持最差）

## 四、接口设计

### 4.1 POST /api/voice/asr

```
Content-Type: multipart/form-data
字段：file(音频), format(wav|amr|m4a), sample_rate(16000), language(zh)
响应：{"text": "今天好累啊", "duration_ms": 2100, "provider": "local"}
```

异常：音频 > 60s → 413；识别为空 → 200 且 `text=""`（前端提示重说）

### 4.2 POST /api/voice/tts

```
Content-Type: application/json
请求：{"text": "嗯……你今天辛苦了", "voice_id": "female_soft", "speed": 1.0, "format": "mp3"}
响应：audio/mpeg 二进制流
响应头：X-Cache: hit|miss
```

设计要点：
- **文本哈希缓存**：`sha1(text + voice_id + speed)` → `data/cache/tts/{hash}.mp3`，重复句子直接命中，省费用
- **临时文件清理**：`data/tmp/voice/` 保留 24h，启动时和每小时各清一次
- 单次文本上限 200 字，超出由前端切句

### 4.3 POST /api/voice/tts/batch（可选，M1.1）

一次请求多句，返回音频数组，减少 HTTP 往返。M1.0 不做。

### 4.4 GET /api/voice/voices

返回可用音色列表（`id`、`name`、`gender`、`sample_url`），供设置面板选择。

## 五、记忆检索升级（M1 并行任务）

### 5.1 当前状态

已实现：jieba 关键词匹配 + 日期近度加权 + 零命中兜底注入最近记忆。

已暴露的短板（本次联调实测）：
- 问「你还记得我叫什么、是做什么的吗」时，关键词「叫/什么/做」太泛，关键词匹配零命中，靠兜底才答对
- 换一种说法（「我上次说的那个事你还记得吗」）几乎必然零命中
- 同义表述无法召回（「失眠」与「睡不着」）

### 5.2 升级方案：混合检索

```
query
  │
  ├─► 路径1：关键词匹配（现有，< 20ms）      ──┐
  │                                            ├─► RRF 融合排序 ─► top-K 注入
  └─► 路径2：向量相似度（新增，< 150ms）      ──┘
                │
                └─ 记忆条目 embedding，本地持久化
```

- 向量库：**chromadb**（嵌入式、纯 Python、数据落 D 盘 `backend/data/vectordb/`，不引入外部服务）
- Embedding：优先用供应商的 embedding 接口（如 BGE / text-embedding-3-small）；DeepSeek 无 embedding，需另配，或用本地 `sentence-transformers`（无需 API，但首次下载模型约 100MB，需放 D 盘）
- 融合：RRF（Reciprocal Rank Fusion），无需调权重
- 降级：向量库不可用 → 自动退回纯关键词 + 兜底，**不阻塞对话**

### 5.3 增量索引

记忆条目写入时同步生成 embedding 并 upsert（`id = sha1(source + date + content)`）。历史条目在服务启动时做一次全量补索引。

## 七、验收标准

- [ ] 长按说话 → 松手 → 3 秒内文字出现在输入框，可编辑后发送
- [ ] 识别失败/为空时有明确提示，不产生空消息
- [ ] 播放按钮可播放 AI 回复，再次点击可停止
- [ ] 连续发送多条时，旧的语音立即停止，不叠音
- [ ] 切句流式 TTS 首音 < 1.5s（云端）/ < 0.5s（设备端）
- [ ] 拒绝麦克风权限后，功能优雅降级而非崩溃
- [ ] 不同角色可绑定不同音色（M1.1）
- [ ] 语义相近但用词不同的提问，能召回相关记忆（M1.2）
- [ ] 向量检索不可用时自动降级，对话不受影响
- [ ] 同一会话重复离开/进入，不再重复蒸馏全量消息

## 八、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 国产 ROM 语音服务缺失 | ASR/TTS 不可用 | 启动时探测能力，缺失则提示并引导用云端方案 |
| 云端 ASR/TTS 费用不可控 | 成本超预期 | 文本哈希缓存 + 单条长度上限 + 用量日志 |
| 切句合成导致语调断裂 | 听感差 | 句子合并阈值（≥12 字或句末标点），并保留整段合成兜底 |
| 录音与播放争抢音频焦点 | 出现回声/无声 | 录音开始前强制停止播放；Android 端配置 AudioFocus |
| 向量库拖慢首字延迟 | 体验退化 | 检索并行 + 200ms 超时直接降级到关键词路径 |
| Web 端插件兼容性差 | 无法在浏览器验证 | Web 只保证文字链路，语音以 Android 为准 |

## 九、与 M2 的衔接

M1 的 `VoiceService` 抽象、`voice_id` 字段、会话软轮换，都会被 M2 的群聊直接复用：
- 群聊中每个角色用各自的 `voice_id`，天然支持"多人对话"的听感区分
- 会话软轮换机制同样适用于群聊会话

### 11.2 设计调整（与初版规划的差异）

1. **放弃 `speech_to_text` 插件，改为自研原生通道。**
   原因：6.x 依赖已移除的 v1 嵌入 API（`Registrar`）无法编译；7.x 引入 `jni` 原生构建，而本机 pub 缓存目录只读，CMake 产物无法写入。
2. **M1.0 阶段 ASR 不再「录音 → 上传后端」**，直接使用设备端识别，减少一次上传与一个后端接口，链路更短。
3. **`shared_preferences` 固定 2.2.2 + `shared_preferences_android` 覆盖为 2.2.3**，避开新版 `jni` 依赖。

### 11.3 构建环境适配（本机特有，已写入配置）

| 问题 | 处理 |
|------|------|
| Windows 未开开发者模式，Flutter 无法创建插件符号链接 | 将 `windows/`、`linux/`、`macos/` 目录改名为 `*_disabled`，仅保留 Android/Web 目标 |
| `D:\software\andriod_data`（全局 Gradle 目录）当前用户不可写 | `GRADLE_USER_HOME` 指向项目内 `.gradle_home`；预置本地 Gradle 8.13 分发避免下载 |
| Java 25 与 Gradle 8.13 不兼容 | `flutter config --jdk-dir=D:\software\JDK`（JDK 21）+ `org.gradle.java.home` |
| Kotlin 守护进程写 `AppData\Local\kotlin` 被拒 | `kotlin.compiler.execution.strategy=in-process`、`kotlin.incremental=false` |
| 项目路径含中文导致 Kotlin 插件 classpath 转义错误 | 建立 ASCII junction：`D:\ai_roleplay → 项目目录`，从 junction 路径构建 |
| `dl.google.com` 在 JVM 下解析失败 | init 脚本把 Google Maven 仓库重写为阿里云镜像 |
| 插件要求 `platforms;android-33` 但 SDK 只装了 34/35/36 | init 脚本统一子工程 `compileSdk = 36` |
| Flutter 要求 Gradle ≥ 8.14，本机只有 8.13 | 构建时加 `--android-skip-build-dependency-validation` |

### 11.4 已验证

- `flutter test` **7/7 通过**，其中 4 个是语音链路测试：
  - ASR：调用原生 `start`，并能接收 `onResult`（中间结果 + 最终结果）
  - ASR：原生 `onError` 能正确记录错误并结束识别

### 12.1 增量蒸馏（B-S01）

`summary.md` 的 front matter 新增两个字段：

```yaml
distilled_upto: 8      # 已处理到第几条消息
segment_count: 2       # 已写入几个片段
```

- 每次蒸馏只处理 `distilled_upto` 之后的新消息，摘要按「## 片段 N（第 a-b 条）」追加
- 没有新消息时直接跳过，不再重复调用 LLM、不再重复写记忆

| 场景 | 结果 |
|------|------|
| 首次蒸馏 | `distilled_upto=4`，`segment_count=1` |
| 无新消息重复蒸馏 | 片段数不变、内容未重复追加 |
| 产生新消息后蒸馏 | 游标 4 → 8，新增第 2 个片段 |

### 12.2 会话软轮换（B-S02）

`GET /api/chat/history` 在读取最近会话时判断是否需要轮换：

- 消息数 ≥ `SESSION_MAX_MESSAGES`（默认 60）
- 或会话跨天（首条消息日期 ≠ 今天）

满足条件时：把旧会话送去后台蒸馏，返回 `session_id=null`（前端据此开新会话），
但历史消息照常返回用于展示。前端 `loadHistory` 已能处理 `sessionId=null`。

验证：构造 61 条消息的会话后请求历史接口 → `rotated=true`、`session_id=null`、仍返回 61 条消息。

### 12.3 闲置会话自动蒸馏（已完成）

详细设计里蒸馏的触发条件之一是「会话闲置超过 30 分钟」，此前只有前端离开页面时调用 `/end`，

## 十三、后端语音识别兜底（2026-11-15）

### 13.1 背景

系统 `SpeechRecognizer` 依赖设备预装语音服务。实测 MuMu（Android 15）与 AOSP 镜像
都没有 `RecognitionService`（`cmd package query-services -a android.speech.RecognitionService`
返回 `No services found`），ASR 无法在模拟器上验收。

因此新增「录音上传 + 后端识别」作为兜底：设备端只负责录音，识别放在后端，
不依赖 Google 服务，国产 ROM / 模拟器同样可用。

### 13.2 链路

```
长按麦克风
  → AudioRecord（16kHz / 单声道 / 16bit PCM）
  → 停止录音，写标准 WAV 头到 cacheDir
  → POST /api/asr/transcribe（multipart）
  → 后端 whisper.cpp / 云端 ASR
  → 文本回填输入框
```

设备端优先使用系统识别；`isRecognitionAvailable=false` 时自动切到录音上传，
麦克风按钮不再置灰，录音条显示「松手后自动转文字」，识别中显示「正在识别…」。

### 13.3 接口与配置

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/asr/status` | 返回 `{available, provider}`，App 启动时探测 |
| POST | `/api/asr/transcribe` | 上传 WAV（≤10MB）返回 `{text}` |

```env
ASR_PROVIDER=local            # local | openai | disabled
ASR_LANGUAGE=zh
WHISPER_BIN=../tools/whisper/Release/whisper-cli.exe
WHISPER_MODEL=../tools/whisper/ggml-base.bin
# ASR_PROVIDER=openai 时：ASR_API_BASE / ASR_API_KEY / ASR_MODEL
```

本地识别使用 whisper.cpp v1.9.2 + `ggml-base.bin`（约 141MB），单次 5 秒中文语音约 1.3s。

### 13.4 验证

- 后端接口：用 Windows SAPI（Huihui 中文音色）合成
  「你好，今天天气不错，我们晚上一起去吃饭吧。」→ 上传 → 返回
  `你好,今天天气不错,我们晚上一起去吃饭吧。`（完全一致）
- Flutter 测试新增 2 项：系统识别不可用时走后端录音并回填文本、后端失败时复位状态，
  整体 **16/16** 通过
- 相关文件：`backend/app/services/asr_service.py`、`backend/app/api/asr.py`、
  `frontend/.../MainActivity.kt`（AudioRecord + WAV）、`voice_service.dart`、`voice_provider.dart`

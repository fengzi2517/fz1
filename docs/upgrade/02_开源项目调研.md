# S2 · 开源「AI 角色扮演聊天」项目调研

> 调研目的：为 `role_play`（FastAPI 后端 + Flutter 前端）的升级方案提供机制级依据。
> 调研方式：WebSearch / WebFetch 抓取官方文档、GitHub 仓库 README 与规范文件；GitHub 活跃度数据于 **2026-11-26 通过 GitHub REST API 实测**（`api.github.com/repos/{owner}/{repo}`，取 `stargazers_count` / `language` / `pushed_at`）。
> 配套文档：本目录 `01_代码逻辑分析.md` 已逐行核实 role_play 现状，本文「可借鉴点」均映射到该文的问题编号（D1–D8 多对话、G1–G9 群聊、§3.2 记忆断点、§6 横切问题）。
> 重要更正：任务背景推测存储为「SQLite/JSON」，但代码分析证实 role_play 实为**纯文件存储（Markdown + JSONL，无数据库）**，路径 `data/users/{uid}/…`。本文据此给出落地建议。

## 0. role_play 现状速览（升级的出发点）

| 维度 | 现状（代码证实） | 主要缺口 |
|---|---|---|

## 2. SillyTavern（重点：机制最完整，优先借鉴）

- **定位**：本地部署的角色扮演聊天前端，接任意 OpenAI 兼容/Kobold/NovelAI 等后端；社区角色卡、Lorebook、扩展生态的事实标准。
- **技术栈**：Node.js + Express 后端，原生 JS/HTML 前端；聊天以 **JSONL 文件**存储（与 role_play 同构，可直接对照）。
- **活跃度**：36,112★，2026-11-22 仍在更新。
- 来源：[仓库](https://github.com/SillyTavern/SillyTavern)、[官方文档](https://docs.sillytavern.app/)、[World Info 中文文档](https://docs.eigeen.cc/usage/core-concepts/worldinfo/)、[Chat Vectorization 文档](https://github.com/SillyTavern/SillyTavern-Docs/blob/main/Extensions/Chat-vectorization.md)、[聊天文件管理](https://github.com/SillyTavern/SillyTavern-Docs/blob/main/Usage/chatfilemanagement.md)、[Character Card V3 规范](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md)。

### 2.1 World Info / Lorebook（关键词触发的动态字典）★核心借鉴

机制：把世界观/设定拆成「条目」，每条有关键词；**仅当最近聊天文本命中关键词时，才把该条目内容注入 prompt**，从而用少量 token 承载海量设定。

- **激活策略**：
  - `normal`（关键词触发）：扫描聊天文本命中主关键词才激活。
  - `constant`（常驻）：始终注入，不受关键词约束，**优先占用预算**。
  - `vectorized`（向量化）：放弃关键词，改用**相似度检索**激活（与 Vector Storage 共用 embedding）。
- **次要关键词 + Selective**：开启 Selective 后需「主关键词 AND 次要关键词」同时命中才注入，降低误触发。
- **插入位置与深度**：可插到「角色定义前/后」，或 `@Depth`（按深度插到聊天历史的指定位置，可指定 role=system/user/assistant）；`插入排序(order)` 值越大越靠近上下文末尾（影响越大）。
- **扫描深度(scan depth)**：最多回扫多少条消息找关键词，默认 2，最多叠加 10 组消息。
- **Token 预算**：默认占上下文 **25%**，可设绝对上限；预算耗尽即停止激活。优先级：常驻 > 高 order > 直接关键词命中 > 递归命中。
- **递归扫描(recursive)**：条目内容里提到别的关键词可连锁激活（例：提到 Bessie → 拉出「Bessie 是牛，朋友是 Rufus」→ 再拉出「Rufus 是狗」）。可设「不可递归」防止爆炸。
- **匹配选项**：区分大小写、整词匹配（避免 king 命中 liking）。
- **角色 Lore 绑定 + 合并策略**：可给角色挂专属 Lorebook，与全局 Lore 合并，策略有「均匀排序（默认）/ 角色 Lore 优先 / 全局 Lore 优先」。
- **进阶时序控制**（社区扩展/新版）：`sticky`（命中后持续 N 条）、`cooldown`（触发后冷却 N 条）、`delay`（首次命中后延迟 N 条才注入）、`inclusion group`（同组条目按优先级择一/择多注入，防互斥设定同时出现）。
- **V3 装饰器**：Lorebook 条目支持 `use_regex` 与 `@@` 装饰器（`activate_only_after`/`activate_only_every`/`keep_activate_after_match`/`dont_activate_after_match`/`depth`/`role`/`scan_depth`/`position`），实现精细时序。
- **写作建议**：每条 ≤50 token、自包含（AI 看不到触发关键词本身）、条目间可互相引用。

> **对 role_play 的映射**：role_play 角色设定是整块 `profile.md` 全量注入，无 Lorebook。可新增「关键词条目表 + 扫描器 + token 预算」，把世界观/配角/地点拆条按需注入，直接缓解 D6（无 token 预算）与 §6.2（检索质量）。constant 条目 ≈ 现有角色设定，normal 条目 ≈ 新增按需设定。

### 2.2 Vector Storage / Chat Vectorization（聊天向量化）★核心借鉴

把历史消息向量化，按当前对话语义召回「过去的事件」，弥补固定窗口失忆。官方参数（实测文档）：

- **分块**：每条消息按 **400 字符**切块后 embedding，后台异步逐条入库。
- **查询**：用**最近 2 条消息**拼成 query 向量。
- **相似度阈值**：默认 **25%（0.25）**，低于阈值不召回。
- **Insert# = 3**：每次注入召回的块数。
- **Retain# = 5**：最近 5 条消息保留原文不向量化（避免与近期窗口重复）。
- **注入位置**：召回内容作为「past events」插到 prompt 顶部/底部，可 shuffle。
- **实验性向量摘要**：先对消息摘要再 embedding，召回时取回原文（省 embedding 成本、提语义密度）。
- **缓存警告**：向量召回内容每轮变化，会**破坏 prompt 前缀缓存**（与 Anthropic/OpenAI prompt caching 冲突），官方明确提示需权衡。
- 与 Data Bank 共用同一 embedding 源。

> **对 role_play 的映射**：role_play **无向量检索**（§3.2 重大缺口），jieba 子串匹配召回不到「我们上次去的那家餐厅」→「和用户去了海底捞」。可直接照搬 ST 参数（400 字符块 / query=最近2条 / 阈值0.25 / Insert3 / Retain5），后端用 `sqlite-vec` 或 Chroma 落向量（纯文件存储可平滑加一个向量索引文件），与现有 jieba 召回做**混合检索**。注意缓存警告：role_play 用 DeepSeek，前缀缓存收益需评估。

### 2.3 Data Bank / RAG（文档知识库）

- **三种作用域**：global（全局）/ character（角色专属）/ chat（当前会话专属）。
- **数据源**：上传文件、网页、Wiki、YouTube 字幕（经服务端插件抓取）。
- 与 Chat Vectorization 共用 embedding，统一向量检索注入。

> 借鉴：role_play 可加「角色知识库」作用域（角色专属文档/设定集），按会话/角色/全局三级隔离，复用同一向量索引。

### 2.4 Summarize（滚动摘要）★核心借鉴

- **滚动摘要**：随对话推进增量更新一段摘要，存到**聊天文件元数据**里「最后被摘要的消息」处。
- **回滚**：编辑/删除已摘要消息时摘要回滚重算；可暂停。
- **注入**：通过 `{{summary}}` 宏注入，位置/深度类似 Author's Note（可配）。
- **更新频率**：默认每 10 条消息更新一次；有启发式「魔法棒」自动间隔。
- 后端：Main API（用主 LLM）或已废弃的 Extras 专用模型。

> **对 role_play 的映射（高优先级）**：role_play 已生成 `summary.md` 分段摘要，但**从不回注单聊上下文**（§3.2 断点、D3 跨天失忆）。ST 的做法正是「摘要随会话滚动 + 注入 prompt」。role_play 只需在 `chat_service.build_messages` 里把 `summary.md` 作为一条 system 注入（位置/深度可配），即可低成本修复「会话轮换后失忆」。群聊已这么做（`GROUP_CONTEXT_TEMPLATE` 注入概要），单聊补齐即可。

### 2.5 qvink/MessageSummarize 扩展（逐条摘要 + 短/长期记忆）

- **逐条消息摘要**：每条消息附一个短摘要（非整段滚动）。
- **短期记忆**：自动轮转、按 token 预算保留最近若干条摘要。
- **长期记忆**：用户手动「标星(brain)」的摘要永久保留。
- **无 embedding**：纯摘要文本，靠注入阈值控制。
- **缓存友好**：注入阈值「冻结」——摘要内容稳定到一定量才更新注入，减少前缀变动。
- **Save Context**：可移除已被摘要覆盖的原始消息以省 token。
- `/qm-*` 斜杠命令管理。

> 借鉴：role_play 可引入「短期摘要（自动轮转、token 预算）+ 长期记忆（重要事实标星）」双层，替代当前「摘要只用于提取、不回注」的断链；其「注入阈值冻结」思路可缓解向量召回破坏缓存的问题。

### 2.6 群聊发言调度 ★核心借鉴

- **三种模式**：
  - `Manual`：用户 `/trigger` 手动点名某角色发言。
  - `Natural Order`（自然顺序，默认）：解析**最后一条消息里整词匹配的角色名提及** → 被点名者优先；否则按各角色 **talkativeness（健谈度 0–100%，默认 50%）** 加权随机抽取；无人命中则随机兜底。
  - `List Order`：按成员列表顺序轮转。
- **Allow Self Responses**：允许角色连续自说自话。
- **Force Talk**：强制某角色发言。
- **Auto-mode**：约 5s 间隔自动推进生成（角色间自动接话）。
- **生成模式**：`swap character cards`（每轮只把当前发言者卡换入，其余角色作为背景）vs `join/merged cards`（合并所有成员卡）——影响 token 与视角。
- **mute**：静音某成员（不参与调度）。

> **对 role_play 的映射（高优先级）**：role_play 群聊只有 round_robin 全员必发言 + target 指定（G1 无智能调度、G2 轮转起点基于窗口内轮次会抖动）。可借鉴 ST「Natural Order」：**@提及整词解析 → talkativeness 加权随机 → 兜底**，让角色会「沉默/插话/抢话」，并给每个角色加 talkativeness 字段。轮转起点应基于**全局用户轮次**而非窗口内（修 G2）。

### 2.7 会话分支 / 检查点 / Swipe ★核心借鉴

- **Checkpoint（检查点）**：克隆当前聊天到某条消息为止，**不切换**，作为存档点。
- **Branch（分支）**：克隆并**切换**到新分支，从该点展开不同剧情；分支以文件名链接父聊天。
- **Swipe**：同一条 AI 回复可左右滑动切换多个候选生成（重新生成不丢旧版本）。
- **JSONL 导出/导入**：聊天可整体导出/导入。

> **对 role_play 的映射**：role_play 无消息级操作（D2 无重新生成/编辑/删除/分支）、旧会话不可达（D1）。可借鉴：① 消息存多候选（swipe）；② 会话目录支持「分支」（克隆 history.jsonl 到某条 + parent 链接）；③ 会话列表 UI 暴露所有会话（修 D1）。Letta 的 `conversations.fork` API 是同一思路的服务端实现。

### 2.8 Character Card V2 / V3 规范 ★核心借鉴

- **V2**（`chara_card_v2`）：JSON 嵌进 **PNG 的 `chara` tEXt 块**（base64），图片即卡片，可分享。字段：`name/description/personality/scenario/first_mes/mes_example/system_prompt/post_history_instructions/alternate_greetings/tags/creator/character_version/extensions/character_book(内嵌Lorebook)`。
- **V3**（`chara_card_v3`）：新增 `ccv3` PNG 块；**CHARX** = zip 包（`card.json` + `assets/{type}/…`），资产用 `embeded://` URI 引用；新增字段：
  - `assets[]`（图标/表情/背景/用户图标等，`{type,uri,name,ext}`）
  - `nickname`（昵称，影响提及解析）
  - `group_only_greetings[]`（仅群聊用的开场白）
  - `creator_notes_multilingual`、`source[]`、`creation_date/modification_date`
  - Lorebook 增强：`use_regex` + `@@` 装饰器（见 2.1）
  - 宏语法：`{{random}}`/`{{pick}}`/`{{roll}}`/`{{hidden_key}}`（随机/掷骰/隐藏键）
- 规范由 RisuAI 作者 kwaroran 维护，ST/AIRI 等兼容。

> **对 role_play 的映射**：role_play 角色卡创建后**丢弃原始人设文本**、不兼容社区标准、无头像/表情/开场白/示例对话字段（§6.8）。建议：① 保留原始卡 JSON；② 实现 V2/V3 导入导出（PNG tEXt 解析 + CHARX zip），直接接入社区海量角色卡；③ 补 `first_mes/alternate_greetings/mes_example/assets(表情差分)/nickname/group_only_greetings` 字段。AIRI 的 `packages/ccc` 是现成的 CCv3 编解码库可参考。

## 3. RisuAI（分层记忆 + 脚本/插件扩展）

- **定位**：跨端角色扮演客户端（Web/桌面/移动），强调分层记忆与高度可定制。
- **技术栈**：**Svelte 5 + TypeScript + Tauri 2.5 + Vite + Tailwind**；GPL-3.0。
- **活跃度**：1,871★，2026-11-26 活跃。

## 6. Letta / MemGPT（OS 分页隐喻的有状态记忆）★记忆架构重点借鉴

- **定位**：有状态 Agent 框架，把 LLM 有限上下文当作「内存」，用 OS 分页思想管理无限记忆。
- **技术栈**：Python；Postgres + 向量索引；提供 REST API + SDK + ADE（Agent 开发环境）。25,559★，2026-10-18。
- 来源：[仓库](https://github.com/letta-ai/letta)、[Memory Blocks 官方文档](https://docs.letta.com/guides/agents/memory-blocks)、[Context Hierarchy](https://docs.letta.com/v1-sdk/memory/context-hierarchy/)、[Archival Memory](https://docs.letta.com/v1-sdk/memory/archival-memory/)、[Sleep-time Agents](https://docs.letta.com/guides/agents/sleep-time-agents)。

### 6.1 上下文层级（Context Hierarchy）

- **Core Memory（核心记忆 / memory blocks）**：**始终在上下文里、无需检索**。
- **Recall Memory（回忆记忆）**：可搜索的完整对话历史。
- **Archival Memory（档案记忆）**：外部向量库（Postgres+vector），无限容量，按需检索。

### 6.2 Memory Blocks 结构 ★核心借鉴

实测官方文档，block 以 XML 式前缀注入 prompt：

```xml
<memory_blocks>
  <persona>
    <description>The persona block: Stores details about your current persona…</description>
    <metadata>- chars_current=128 - chars_limit=5000</metadata>
    <value>I am a helpful assistant named Sam…</value>
  </persona>
  <human>
    <description>The human block: Stores key details about the person you are conversing with…</description>
    <value>The user's name is Alice. She is a software engineer…</value>
  </human>
</memory_blocks>
```

- 字段：`label`（唯一标识）+ `description`（用途说明，**决定 Agent 如何读写该块**）+ `value`（内容）+ `limit`（字符上限，硬约束）。
- **description 至关重要**：Agent 靠它理解块的用途；`persona`/`human` 有自动生成默认描述。
- **read_only**：可设只读块（共享策略/组织知识，Agent 不可改）。
- **共享块**：多 Agent 挂同一 block，一处更新处处可见（多 Agent 协调原语）。
- 用途灵活：知识、指南、状态跟踪、scratchpad、`emotional_state`/`performance_tracking`（涌现行为）。

> **对 role_play 的映射**：role_play 的 `long-term.md`（用户级）+ `memory.md`（角色×用户）≈ 两个 always-visible 块，但**无 limit、无 description 引导、无自我编辑**。可借鉴：① 给每块加字符上限（修 §6.1 无限增长）；② 加 description 让 LLM 知道如何维护；③ `write_user_profile()` 无调用方（§3.2）→ 用 block 自我编辑工具补上「用户画像随对话成长」闭环。

### 6.3 自我编辑记忆工具 ★核心借鉴

Agent 通过内置工具**自主读写记忆**：

- `core_memory_append` / `core_memory_replace`：增/改核心块。
- `archival_memory_insert` / `archival_memory_search`：写/向量检索档案记忆。
- `conversation_search`：搜索历史。

> **对 role_play 的映射（高优先级）**：role_play 的 `RECALL_TOOL` 定义了却**从未传给 LLM**（§3.2），LLM 无法主动决定回忆/记录。借鉴 Letta：把 recall/记忆写入做成**真正可用的工具**传给 LLM，让它主动「想起该查记忆」「记下重要事实」，而非仅靠 16 个关键词规则触发。

### 6.4 记忆压力驱逐 + Sleep-time Agents ★核心借鉴

- **记忆压力驱逐**：上下文接近上限时，自动把约 **30% 旧历史摘要**后移出核心上下文（分页换出）。
- **Sleep-time 后台 Agent**：主 Agent 每约 **5 步**，后台触发一个**更强模型**的 sleep-time agent，异步整理/更新核心记忆（不阻塞对话）。
- **Git-backed 记忆版本化**（1.0）：记忆变更可版本回溯。
- **conversations.fork API**：会话分叉（同 ST 分支）。

> **对 role_play 的映射**：role_play 蒸馏是「离开/轮换/闲置/群阈值」四路触发，但**同步阻塞、失败静默丢记忆**（§3.1）。借鉴 sleep-time：把蒸馏改为**异步后台 worker**（ stronger model 可选），主聊天不阻塞；记忆压力驱逐 ≈ 修 D6（固定 20 条窗口）→ 按 token 预算动态摘要换出。Git 版本化可解决「摘要写入但提取失败记忆丢失」的回滚问题。

## 7. mem0（抽取→更新记忆管线）★记忆治理重点借鉴

- **定位**：通用 LLM 记忆层，解决「长期记忆抽取/更新/冲突消解」。
- **技术栈**：Python；向量库 + 可选图数据库。69,500★，2026-11-25 活跃。
- 来源：[仓库](https://github.com/mem0ai/mem0)、[文档](https://docs.mem0.ai/)、论文《Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory》。

### 7.1 两阶段管线 ★核心借鉴

1. **Extraction（抽取）**：从最近对话 + 滚动摘要中，LLM 抽取候选事实/记忆。
2. **Update（更新）**：对每条新记忆，检索**语义相似的旧记忆**，LLM 决策四选一：
   - `ADD`（新增）/ `UPDATE`（更新旧条目）/ `DELETE`（删除矛盾旧条目）/ `NOOP`（无操作）。
- **作用域**：`user_id` / `session_id` / `agent_id` 三级隔离。
- API：`add()` / `search()`。
- **图变体 Mem0^g**：实体-关系图记忆，支持关系推理。

### 7.2 新版 v3 演进

- **单次调用 ADD-only**：简化管线（抽取+合并一次完成），降延迟。
- **实体存储**：`linked_memory_ids` 关联实体，检索时实体 boost。
- **三信号检索**：语义 oversample + **BM25** + 实体 boost 融合。
- LOCOMO 基准宣称：准确率 +26%、p95 延迟 −91%、token −90%（相对全上下文）。

> **对 role_play 的映射（最高优先级）**：role_play 去重**仅 jieba 词面 0.6 阈值**，「用户喜欢猫」→后来「养狗并讨厌猫」**两条并存不更新**（§3.1、§6.3 记忆治理缺失）。mem0 的 **ADD/UPDATE/DELETE/NOOP 冲突消解**正是解药：把现有「提取 JSON → 词面去重 → 追加」升级为「提取 → 向量召回相似旧记忆 → LLM 决策增/改/删/无操作」。作用域三级（user/session/agent）≈ role_play 的 user/角色×用户/会话。三信号检索（语义+BM25+实体）可替代纯 jieba 子串匹配。

## 8. LangGraph / AutoGen（多 Agent 编排 → 群聊调度）★群聊借鉴

- **定位**：LangGraph 是状态图多 Agent 编排框架；AutoGen 是微软多 Agent 对话框架。
- **技术栈**：Python。LangGraph 45,455★，2026-11-26 活跃。
- 来源：[LangGraph 仓库](https://github.com/langchain-ai/langgraph)、[多 Agent 概念文档](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。

### 8.1 编排模式

- **StateGraph + 条件边 + checkpointer**：节点=Agent/工具，条件边=路由决策，checkpointer=状态持久化（可恢复/分叉）。
- **Supervisor（监督者）**：中心 Agent 用 `create_handoff_tool` 决定把任务交给谁，返回 `Command(goto=下一节点)`。→ **LLM 决定下一个发言者**。
- **Swarm（群体）**：Agent 间**对等 handoff**，记住「最后活跃发言者」，去中心化接力。
- **Orchestrator-Workers**：`Send` 扇出并行子任务再聚合。→ **并行生成**。
- AutoGen `SwarmGroupChatManager.select_speaker`：群聊发言者选择器（可 LLM/规则/轮转）。

> **对 role_play 的映射**：role_play 群聊串行全员发言（G1 无调度、G4 串行延迟）。借鉴：① **Supervisor 模式**——用一个轻量 LLM 调用决定「谁该说话/谁沉默」，替代 round_robin（修 G1）；② **Swarm**——基于 @提及/最后发言者接力；③ **Orchestrator-Workers 并行**——无依赖的成员发言可并行生成（修 G4 串行延迟）；④ checkpointer ≈ 群聊会话/分支（修 G7 群无会话概念）。role_play 用 FastAPI，可不引入 LangGraph 重依赖，仅借鉴其「条件路由 + 并行扇出 + 状态持久化」思想自研调度器。

- 机制：**多角色独立管理**（各角色独立聊天记录+朋友圈，互不串数据）、**AI 朋友圈动态**（角色发日常，可点赞留言）、**主动消息**（AI 按自己节奏主动发）、**定时任务推送**。

> **对 role_play 的映射（高价值）**：同 Flutter 栈、同「多角色+主动消息」场景。可直接参考其：① 微信式会话列表 UI（修 D1 旧会话不可达）；② 多角色数据隔离；③ 朋友圈/动态作为主动消息的新载体；④ 定时任务推送机制。建议 clone 研读其 Provider 状态管理与推送实现。

## 12. 最值得借鉴的 10 个机制（映射 role_play 落地）

> 按「优先级 × 落地成本」排序，每条标注修复的代码问题编号与具体落地路径（FastAPI + Flutter + 纯文件存储）。

### ① mem0 式记忆冲突消解管线（最高优先级）
- **来源**：mem0 Extraction→Update（ADD/UPDATE/DELETE/NOOP）。
- **修复**：§3.1/§6.3「词面去重 0.6、矛盾事实并存不更新」。
- **落地**：把 `distill_service` 的「提取 JSON→jieba 去重→追加」改为「提取候选→**向量召回相似旧记忆**→LLM 决策增/改/删/无操作→写回」。`memory_service.is_duplicate()` 升级为语义+决策。纯文件存储可加一个向量索引（sqlite-vec/Chroma）。

### ② 向量语义检索 + 混合召回（最高优先级）
- **来源**：ST Chat Vectorization（400 字符块/query=最近2条/阈值0.25/Insert3/Retain5）+ mem0/Hindsight 三/四路召回（语义+BM25+实体+时间）。
- **修复**：§3.2/§6.2「无向量、jieba 子串召回不到语义」。
- **落地**：后端加 embedding worker，对 `history.jsonl`/`memory.md` 分块向量化；recall 改为「向量 + 现有 jieba/BM25」混合，保留零命中兜底。注意 ST 缓存警告（DeepSeek 前缀缓存收益需评估）。

### ③ 摘要回注单聊 + 分层记忆（高优先级，低成本）
- **来源**：ST Summarize 滚动摘要注入 + RisuAI HypaMemory V3「最近+场景相似+随机」+ qvink 短期/长期双层。
- **修复**：§3.2 断点、D3「summary.md 从不回注、跨天失忆」。
- **落地**：`chat_service.build_messages` 增加一条 system 注入 `summary.md`（群聊已有，单聊补齐）；摘要分「短期自动轮转（token 预算）+ 长期标星」；注入阈值冻结减少缓存抖动。

### ④ Letta 式记忆块 + 自我编辑工具（高优先级）
- **来源**：Letta memory blocks（label/description/value/limit）+ `core_memory_append/replace`、`archival_memory_search` 工具 + sleep-time 异步整理。
- **修复**：§3.2「RECALL_TOOL 定义但从未使用、write_user_profile 无调用方」、§6.1「long-term.md 无限增长」、§3.1「蒸馏同步阻塞/失败丢记忆」。
- **落地**：给 `long-term.md`/`memory.md` 加字符上限与 description；把 recall/记忆写入做成**真正传给 LLM 的工具**；蒸馏改异步后台 worker（sleep-time），失败可回滚（Git 版本化思路）。

### ⑤ 群聊智能发言调度（高优先级）
- **来源**：ST Natural Order（@提及整词解析 + talkativeness 加权随机 + 兜底）+ LangGraph supervisor/swarm。
- **修复**：G1「无智能调度、全员必发言」、G2「轮转起点基于窗口内轮次抖动」。
- **落地**：`group_service` 调度器改为「解析最后消息@提及 → 各角色 talkativeness（新增字段）加权随机 → 兜底」；可选轻量 LLM supervisor 决定谁说话/沉默；轮转起点用全局用户轮次。

### ⑥ 会话分支 / Swipe / 旧会话可达（高优先级）
- **来源**：ST checkpoints/branches/swipe + Letta `conversations.fork` + ZeroChat 微信式会话列表。
- **修复**：D1「旧会话不可达」、D2「无重新生成/编辑/删除/分支」、G7「群无会话概念」。
- **落地**：消息存多候选（swipe）；会话目录支持克隆+parent 链接（分支）；`api/conversations` 暴露全部会话 + Flutter 会话列表页；群聊引入 session 子目录。

### ⑦ Token 预算 + 动态上下文裁剪（中高优先级）
- **来源**：ST World Info token 预算（默认 25%）+ Letta 记忆压力驱逐（~30% 旧历史摘要换出）+ KoboldCpp ContextShift。
- **修复**：D6「固定 20 条窗口、长消息爆 token」、G9「群概要 4000 字符硬截断截在句中」。
- **落地**：`build_messages` 按 token 预算（而非条数）动态装配：常驻设定 > 摘要 > 召回 > 近期历史，超限摘要换出；群概要按句边界截断。

### ⑧ 角色卡 V2/V3 标准化 + 资产/表情/开场白（中高优先级）
- **来源**：Character Card V2/V3 规范（PNG tEXt/CHARX、assets/nickname/group_only_greetings/alternate_greetings/mes_example）+ AIRI `packages/ccc` 编解码 + RisuAI 情绪图片。
- **修复**：§6.8「丢弃原始人设、不兼容社区卡、无头像/表情/开场白/示例对话」。
- **落地**：保留原始卡 JSON；实现 V2/V3 PNG/CHARX 导入导出；补 `first_mes/alternate_greetings/mes_example/assets(表情差分)/nickname`；Flutter 按情绪标签切换表情差分。

### ⑨ 主动消息时机引擎 + 情绪/关系状态机（中优先级）
- **来源**：jiwen 5 漂移轴 + revive-companion 泊松/贝叶斯/信息增益 + astrbot proactive DND + Aura/OpenHer 情绪状态机。
- **修复**：主动性时机粗糙、G5「无角色关系/态度状态」。
- **落地**：IdleSweeper 升级为「情绪漂移轴 + 用户状态推断 + DND」驱动；新增角色关系/情绪变量（trigger 脚本思路），驱动表情与主动消息；纯 Python 可落地（jiwen ~500 行）。

### ⑩ 群聊并行生成 + 缓存友好 + 防复读（中优先级）
- **来源**：LangGraph orchestrator-workers 并行扇出 + Paramecium/Pawwake prompt-cache 分区 + DuduLove 召回账本防反复浮现 + RisuAI 随机摘要注入。
- **修复**：G4「串行延迟线性叠加」、G5「无防复读」、G8「打断半截话污染记忆」、G9「无缓存」。
- **落地**：无依赖成员发言并行生成（asyncio.gather）；记忆/召回内容分区稳定前缀以友好缓存；召回账本防同一记忆反复注入；打断半截话标记不进蒸馏（修 G8）；旁路交互（朋友圈/动态）独立存储不污染主日志（柚月思路）。

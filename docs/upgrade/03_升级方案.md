# S3 · role_play 商业级升级方案

> 依据：`01_代码逻辑分析.md`（现状与问题编号 D1–D8 / G1–G9 / §3.2 记忆断点 / §6 横切问题）+ `02_开源项目调研.md`（16 个项目机制级调研，借鉴点 ①–⑩）。
> 目标：把 role_play 从"能用的个人玩具"升级为**可对外运营的商业级角色扮演聊天产品**——记忆可靠、群聊生动、会话自由、角色生态互通、语音自然、服务可运维。

## 1. 产品定位与商业级定义

**定位**：微信式体验的 AI 角色伴侣应用（Flutter 多端 + 自托管后端），主打"记得住、聊得活、角色生态开放"。对标 SillyTavern 的能力深度 + 星野/Glow 的移动体验 + ZeroChat 的微信式交互。

**商业级验收线（Definition of Commercial-Grade）**：

| 维度 | 硬指标 |
|---|---|
| 安全 | 鉴权全覆盖、租户隔离、无路径穿越、内容安全过滤、密钥不落客户端 |
| 可靠性 | 记忆写入事务化（蒸馏失败可重试不丢数据）、并发写无竞态、服务可水平重启 |
| 记忆质量 | 语义召回命中率 ≥80%（评测集）、矛盾事实消解率 ≥90%、跨会话剧情连续性人工评测 ≥4/5 |
| 性能 | 单聊首 token p95 ≤2.5s；4 人群聊整轮 p95 ≤8s；万条消息会话历史加载 ≤500ms |
| 体验 | 会话分支/重新生成/编辑、群聊智能调度、角色卡 V2/V3 导入导出、表情差分、主动消息+免打扰 |
| 运维 | 结构化日志+指标+告警、Docker 一键部署、数据备份/导出、灰度与回滚 |
| 工程 | 核心链路单测覆盖 ≥70%、CI 门禁、API 版本化 |

**非目标（本期不做）**：Live2D/VRM 重型视觉、自训模型、多实例分布式 WS（Redis）、开放平台插件市场。留作远期。

## 3. 目标架构

```
                        ┌────────────────────────────────────────────┐
 Flutter 多端（Android/iOS/Web/桌面）                                  │
  会话列表(微信式) 聊天(分支/swipe) 群聊(调度可视化) 角色卡库 记忆审计页  │
  语音(流式TTS+barge-in) 表情差分头像 主动消息通知                      │
                        └───────────────┬────────────────────────────┘
                                        │ HTTPS / SSE / WS（JWT 鉴权）
┌───────────────────────────────────────▼────────────────────────────┐
│ FastAPI 主服务（聊天编排，无状态可重启）                               │
│  auth  middleware（JWT + user_id 服务端解析 + 路径校验）               │
│  api/v1: chat / sessions / groups / characters / memory / voice      │
│  ContextAssembler：token 预算分区装配（常驻设定>摘要>召回>近期历史）     │
│  GroupScheduler：@提及 → 健谈度加权 → (可选)LLM supervisor → 并行扇出  │
│  RelationshipEngine：情绪/好感变量，驱动表情与主动消息时机              │
└──────────────┬─────────────────────────────┬───────────────────────┘
               │ 任务队列(SQLite 表即可)        │
┌──────────────▼──────────────┐   ┌───────────▼──────────────────────┐
│ Memory Worker（异步蒸馏）     │   │ LLM Gateway（adapter 升级）        │
│  增量游标+事务：摘要→提取→     │   │  多 provider/退避重试/JSON mode/   │
│  向量召回相似→LLM 决策        │   │  正确 fallback/用量计费埋点        │
│  ADD/UPDATE/DELETE/NOOP      │   │  主模型 + 蒸馏廉价模型分离          │
│  embedding 入库(后台)         │   └──────────────────────────────────┘
└──────────────┬──────────────┘
┌──────────────▼─────────────────────────────────────────────────────┐
│ 存储引擎：SQLite(WAL) + sqlite-vec（单文件，保持"数据全本地"卖点）      │
│  messages(含 candidates/swipe) sessions(含 parent 分支树)            │
│  memory_entries(scope/importance/status/embedding/证据消息id)        │
│  lorebook_entries  characters(原始卡JSON+资产)  groups  relations    │
│  Markdown 降级为**导出/审计视图**（保留人类可读优势，不再是真相源）      │
└────────────────────────────────────────────────────────────────────┘
```

关键决策与理由：
- **SQLite 而非 Postgres**：单机自托管定位，SQLite+WAL 解决锁与 O(n) 问题，sqlite-vec 解决向量索引，保持零外部依赖、一键部署；`data/` 目录即备份单元。多租户 SaaS 化时再迁 Postgres（DAO 层隔离）。
- **Markdown 保留为导出视图**：现有 md 记忆是产品差异化（可审计/可手改），迁移后提供"记忆审计页 + md 导出/导入"，手改 md 可回灌。
- **蒸馏独立 worker**：借鉴 Letta sleep-time / Agnai pipeline，主聊天路径永不阻塞于蒸馏；蒸馏可用更廉价模型。
- **不引入 LangGraph/Celery 重依赖**：调度器自研（~300 行），任务队列用 SQLite 表 + asyncio worker，规模到了再换。

## 5. 核心数据模型草案（P0-2 落地基准）

```sql
-- 会话：分支树 + 群聊统一
sessions(id, user_id, kind TEXT CHECK(kind IN('char','group')),
         character_id, group_id, parent_session_id, branched_at_message_id,
         title, status TEXT DEFAULT 'active',  -- active/archived/trashed
         distilled_upto INTEGER DEFAULT 0, created_at, last_message_at);
messages(id, session_id, seq, role, character_id, name,
         content, candidates JSON,            -- swipe 多候选
         active_candidate INTEGER DEFAULT 0,
         flags JSON,                          -- interrupted/edited/pinned
         summary_covered INTEGER DEFAULT 0, token_count, created_at);
-- 记忆：统一条目表替代 md（scope 三级隔离）
memory_entries(id, user_id, scope TEXT,       -- user/character/group
               character_id, group_id, block_label,
               content, importance REAL, status TEXT,  -- active/superseded/archived
               evidence_message_ids JSON, embedding BLOB,
               created_at, updated_at, last_recalled_at, recall_count);
lorebook_entries(id, user_id, character_id, keywords JSON, secondary_keywords JSON,
```

## 6. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 文件→SQLite 迁移丢数据 | 高 | 迁移脚本幂等+逐条 diff 校验；原文件目录只读保留 ≥2 版本；迁移前自动备份 |
| 向量召回破坏 prompt 前缀缓存、成本上升 | 中 | 召回内容固定放易变后缀区；注入阈值冻结（qvink 式）；DeepSeek 缓存命中率埋点监控 |
| 冲突消解 LLM 误删正确记忆 | 高 | DELETE 仅置 superseded 可恢复；记忆审计页人工兜底；决策日志全留痕 |
| 群聊并行后角色互相接话逻辑错乱（A 引用了还没生成的 B） | 中 | 并行仅用于"同轮各自回应用户"；角色间接话模式仍串行；调度器声明依赖 |
| 蒸馏/embedding 成本失控 | 中 | 廉价模型分离；增量游标保留；每用户配额；夜间批处理 |
| 角色卡社区内容版权/合规 | 中 | 导入卡审核开关；举报通道；NSFW 分级与未成年人模式 |
| 单人开发周期漂移 | 中 | 每阶段独立可发布；P0/P1 为不可跳过主线，P3 各项可裁剪 |
| 不支持 tools 的模型记忆工具失效 | 低 | 保留规则触发回退路径（现状逻辑降级为 fallback） |
